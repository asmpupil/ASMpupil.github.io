Win10PE尝试使用完整UWP过程

一、问题背景与初始尝试

目标是在 Win10 PE 环境下运行原生 UWP 开始菜单（StartMenuExperienceHost.exe）及相关组件（设置、搜索、操作中心）。

现象表现为手动启动进程后 2-3 秒闪退，无任何界面；将 PE 的 WIM 释放到硬盘后正常启动，排除了文件缺失的可能性。

早期无效尝试包括：

  • 补全 UWP 相关服务（AppXSvc、ClipSVC、AppReadiness 等）
  • 删除 MiniNT 注册表项
  • 补充 AppResolver.dll、StartTileData.dll 等文件
结论：并非简单的环境缺失，而是微软在 XAML 框架层面对 PE 环境做了主动检测和限制。

二、崩溃分析：锁定元凶

使用 WinDbg 分析崩溃转储，得到核心调用栈：

Windows_UI_Xaml!FailFastOnUnsupportedLaunch+0xa
  -> wil::details::WilFailFast
    -> KERNELBASE!RaiseFailFastException
      -> ntdll!RtlRaiseNoncontinuableException

异常代码为 c0000409 (STATUS_STACK_BUFFER_OVERRUN)，Subcode 为 0x7 (FAST_FAIL_FATAL_APP_EXIT)。核心拦截函数为 FailFastOnUnsupportedLaunch 及 WilFailFast。

三、其他 UWP 组件的表现

通过分析不同进程的崩溃转储，将失败模式分为三类：

类型 代表进程 失败机制
A型 StartMenuExperienceHost.exe
ShellExperienceHost.exe		 主动快速失败 (FailFast)
B型 SearchApp.exe COM/WinRT 组件激活失败
C型 SystemSettings.exe 等待未就绪的服务/组件，界面卡死

A 型是最普遍、最核心的障碍。

四、逆向工程：挖掘检测逻辑

使用 Ghidra 对 Windows.UI.Xaml.dll 进行静态分析，定位到关键函数调用链：

FrameworkApplicationFactory::Start
  -> FUN_1804bb19c
    -> FUN_1804bc1b4
      -> FUN_1804bbf58 (核心判断)

核心判断逻辑依赖于全局函数指针 DAT_180f60e58。在正常系统下该指针被初始化（非 0），而在 PE 下为 NULL，导致检查失败并触发 WilFailFast。

五、尝试的绕过方案与结果

  • DLL 注入劫持：尝试替换 g_pfnWilFailFast，受限于 UWP 沙盒对路径的访问控制，LoadLibrary 返回失败。
  • AppInit_DLLs 全局注入：进程存活时间显著延长，证明补丁生效，但因全局注入严重影响系统性能且界面仍未出现，放弃该方案。
  • 直接修改 DLL 文件：修补指令为 RET 后仍崩溃，推测原因包括签名强制、存在多个快速失败出口或修补地址不完全正确。
  • 挂起进程 + 远程内存修补：进程存活时间延长，但 UI 仍未渲染，推测卡在后续初始化步骤。

六、当前状态与失败分析

已确认 FailFastOnUnsupportedLaunch 是核心检查点，全局指针 DAT_180f60e58 未初始化是直接原因。然而，即使绕过该检查，开始菜单仍无法完全启动，可能存在其他未发现的检测点或运行时依赖缺失。

七、未来可能的研究方向

  • 深入逆向 FailFastOnUnsupportedLaunch 的所有分支。
  • 使用 WinDbg 进行双机内核调试，观察 XAML 初始化全过程。
  • 彻底对照正常系统的 UWP 初始化日志，补全服务与注册表权限。
  • 研究替换 XAML 框架的可行性（面临签名与兼容性难题）。
  • 放弃 PE，转向精简系统或 PrimoCache 等替代方案。

八、技术经验总结

本次研究完整实践了 WinDbg 崩溃分析、Ghidra 静态逆向、x64dbg 动态调试、DLL 注入、API 钩子及内存修补等技术。虽然未能最终成功，但对 UWP 应用模型、AppContainer 沙盒及 Windows 底层机制有了深入理解。

总结：微软对 WinPE 的限制是系统性的，非单点突破可解。此次研究积累了完整的系统级调试流程经验，具有较高的参考价值。
