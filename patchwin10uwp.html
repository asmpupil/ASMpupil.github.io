Win10PE尝试使用完整UWP过程

一、问题背景与初始尝试

目标：在 Win10 PE 下运行原生 UWP 开始菜单（StartMenuExperienceHost.exe）以及其他 UWP 组件（设置、搜索、操作中心等）。

现象：

  • 手动启动 StartMenuExperienceHost.exe 后进程 2-3 秒闪退，无任何界面。
  • 将 PE 的 WIM 释放到硬盘正常启动，所有 UWP 组件完全正常 → 排除文件缺失。

早期无效尝试：

  1. 补全 UWP 相关服务：启动 AppXSvc、ClipSVC、AppReadiness 等 — 无效。
  2. 删除 MiniNT 注册表项 — 无效。
  3. 补充 AppResolver.dll、StartTileData.dll 等文件 — 无效。

结论：不是简单的环境缺失，而是微软在 XAML 框架层面对 PE 环境做了主动检测和限制。

二、崩溃分析：锁定元凶

使用 WinDbg 分析崩溃转储，得到核心调用栈：

Windows_UI_Xaml!FailFastOnUnsupportedLaunch+0xa
  -> wil::details::WilFailFast
    -> KERNELBASE!RaiseFailFastException
      -> ntdll!RtlRaiseNoncontinuableException
        异常代码: c0000409 (STATUS_STACK_BUFFER_OVERRUN)
        Subcode: 0x7 FAST_FAIL_FATAL_APP_EXIT

关键函数：

  • FailFastOnUnsupportedLaunch — 位于 frameworkapplication_partial.cpp
  • WilFailFast — Windows Implementation Library (WIL) 的快速失败执行体

这两个函数构成了 PE 下 UWP 应用启动的“拦截关卡”。

三、其他 UWP 组件的表现

通过分析不同进程的崩溃转储，将失败模式分为三类：

类型 代表进程 失败机制 调用栈特征
A型 StartMenuExperienceHost.exe
ShellExperienceHost.exe
CallingShellApp.exe
XGpuEjectDialog.exe		 FailFastOnUnsupportedLaunch -> WilFailFast
主动快速失败		 Windows_UI_Xaml!FailFastOnUnsupportedLaunch
B型 SearchApp.exe COM/WinRT 组件激活失败 -> RoFailFastWithErrorContextInternal2 combase!RoFailFastWithErrorContextInternal2
C型 SystemSettings.exe 环境检查通过，但运行时等待未就绪的服务/组件，界面卡死 twinapi_appcore!Event::Wait

结论：A 型是最普遍、最核心的障碍，只要攻克它，大部分 Shell 宿主即可复活。

四、逆向工程：挖掘检测逻辑

使用 Ghidra 对 Windows.UI.Xaml.dll 进行静态分析，顺着调用栈定位到关键函数：

4.1 调用链

FrameworkApplicationFactory::Start
  -> FUN_1804bb19c
    -> FUN_1804bc1b4
      -> FUN_1804bbf58  (核心判断)

4.2 核心判断逻辑（FUN_1804bbf58）

bVar1 = false;
if ( (in_stack_00000038 == 0) && 
     ((in_stack_00000050 & 4) == 0) && 
     (DAT_180f60e58 != 0) )
{
    bVar1 = true;
}
// 如果 bVar1 为 true，则调用 DAT_180f60e58 指向的函数
// 否则最终会调用 FUN_1804bcd0c（触发 WilFailFast）

关键发现：

  • 检查依赖于一个全局函数指针 DAT_180f60e58。
  • 在正常系统下该指针被初始化（值为非 0）；在 PE 下为 NULL，导致检查失败。
  • WinDbg 验证：
    • 正常系统：002e006e 006f0069
    • WinPE：00000000 00000000

4.3 最终执行者：FUN_1804bcd0c

该函数是 WilFailFast 的封装，负责构造异常并调用 RaiseFailFastException。

五、尝试的绕过方案与结果

5.1 DLL 注入劫持 g_pfnWilFailFast

  • 编写 DLL，在 DllMain 中将 g_pfnWilFailFast 替换为自己的空函数。
  • 问题：注入器能成功注入，但 LoadLibraryA 返回 NULL（UWP 沙盒限制 X:\Tools 路径访问）。尝试放置 System32 并设置权限仍失败。

5.2 AppInit_DLLs 全局注入

  • 通过注册表 AppInit_DLLs 让所有 GUI 进程加载补丁 DLL。
  • 效果：系统明显变慢（每个进程循环等待 20 秒），但开始菜单进程存活时间从 1 秒延长到 1 分钟以上，证明补丁生效。
  • 问题：进程虽未崩溃，但界面未出现，怀疑还有第二道关卡（卡在消息循环或服务等待）。因全局注入严重影响体验，放弃该方案。

5.3 直接修改 Windows.UI.Xaml.dll 文件

  • 尝试用 Ghidra 修补 FUN_1804bcd0c 的第一条指令为 RET，导出后替换系统 DLL。
  • 问题：修改后仍然崩溃，且新的 Dump 显示异常反复抛出，最终栈溢出。可能原因：
    • 签名强制导致系统仍加载原始 DLL（尽管设置了 ValidateAdminCodeSignatures）。
    • 存在多个快速失败出口，绕过了一个还有另一个。
    • 修改的地址不正确（但 Ghidra 和 WinDbg 双重确认，可信度高）。

5.4 挂起进程 + 远程内存修补（最终尝试）

  • 编写启动器：挂起创建 StartMenuExperienceHost.exe，轮询等待 Windows.UI.Xaml.dll 加载后，将 DAT_180f60e58 写入一个远程分配的空函数指针（Stub）。
  • 问题：进程存活时间延长，但界面仍然不出现。怀疑仍卡在后续初始化步骤。

六、当前状态与失败分析

已确认：

  • FailFastOnUnsupportedLaunch 是 PE 下阻止 UWP 启动的核心检查。
  • 全局指针 DAT_180f60e58 未初始化是直接原因。

未解决的问题：

  • 即使让该指针通过检查，开始菜单仍无法完全启动，可能还有：
    • 其他未发现的检测点。
    • 运行时依赖的服务或组件仍缺失。
    • 修改的指针值（Stub）虽然通过了检查，但后续初始化中可能被正确调用并需要执行实际功能，空函数导致后续逻辑异常但未崩溃（卡死）。

七、未来可能的研究方向

  1. 更深入地逆向 FailFastOnUnsupportedLaunch：找出所有可能的失败分支，逐一修补或绕过。
  2. 内核调试：使用 WinDbg 双机调试 PE，观察 XAML 初始化全过程，捕捉每一个条件跳转。
  3. 服务与依赖补全：彻底对照正常系统的 UWP 初始化日志（如 TWinUI 事件），补全 PE 中缺失的服务、注册表权限和后台任务。
  4. 替换 XAML 框架：研究是否可以用较早版本或修改过的 Windows.UI.Xaml.dll（不触发 PE 检查）替换，但签名和版本兼容性是大难题。
  5. 放弃 PE，转向精简系统或 PrimoCache：这是当前最务实的替代方案，可以获得完整的 UWP 支持。

八、技术经验总结

  • 熟练使用了 WinDbg 分析崩溃转储，Ghidra 逆向大型 DLL，x64dbg 动态调试。
  • 实践了 DLL 注入、API 钩子、内存修补、PE 文件修补等 Windows 底层技术。
  • 对 UWP 应用模型、AppContainer 沙盒、WIL 库有了深入理解。
  • 认识到微软对 WinPE 的限制是系统性的，非单点突破可解。

本次研究虽然没有最终成功，但完整地走完了“从现象到根因、从猜想到验证、从补丁到部署”的全流程，积累的经验对今后类似的系统级调试和逆向工程具有很高的参考价值。
